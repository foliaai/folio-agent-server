# ADR-0001: WASM 沙箱执行架构（out-of-process）

> 状态：**已接受**（2026-09）
> 上游文档：`docs/智能体平台架构方案.md` §4

## 背景

智能体平台需要执行两类不可信代码：

1. 用户在 DIY 智能体中定义的工具（Python / JS / TS）；
2. LLM 生成的代码（首页 agent 的 `code_execute` 工具）。

2026 年的安全事故给出了明确教训：

- **DEF CON 34 / Cyera**："一个 Pyodide 缺陷打穿七个产品"——Pyodide 的设计假设输入代码可信（shell 与 Python 共享同一块线性内存与文件系统，互相可读写对方的内存和文件）。
- **Cohere Terrarium**（2026-04）：沙箱实现缺陷导致根代码执行 / 容器逃逸。
- wasmsh SECURITY.md 明确承认："Python 是不受约束的（Pyodide target）……限流和沙箱化 Python 执行是宿主的责任。"

隔离强度的事实排序（Qovery 2026 综述 + USENIX Firecracker 论文）：

```
microVM > gVisor > 共享内核容器 >> 同进程 WASM
```

普通 Docker 容器不是不可信代码的安全边界（runc CVE-2019-5736 / CVE-2024-21626）；**WASM 的线性内存边界是强边界，但前提是运行时本身不与业务进程同生共死**。

## 决策

沙箱执行采用**独立 sidecar 进程 + Wasmtime**：

```
API 服务器（agent loop，FastAPI）
   │  spawn / 池化复用
   ▼
沙箱 sidecar 进程（独立可执行，非线程/非 asyncio task）
   └── Wasmtime（Server 方式嵌入 sidecar）
       ├── 每次工具调用 = 独立 Store / Instance（内存、燃料、epoch 全部独立）
       ├── 资源硬限制（见下）
       └── 宿主函数（Host Function）是唯一的 I/O 通道
```

### 进程拓扑细则

- sidecar 由 API 服务器（或 systemd / supervisor）拉起，通过 stdin/stdout（JSON-RPC 风格）或本地 UDS 通信。
- **每次工具调用一个新 Store**；同 Store 不跨调用复用（防状态泄漏）。
- sidecar 满足任一条件即自杀重启：单次调用超时、燃料耗尽仍不返回、内存配额超限、连续 N 次调用失败。
- sidecar 以低权限 OS 用户运行（无 home、无 shell、只读二进制）。
- 高并发时横向起多个 sidecar（简单轮询池），不做线程级共享。

### 资源硬限制

| 资源 | 机制 | 默认值（可配） |
|---|---|---|
| CPU | Wasmtime **fuel**（确定性指令计量）+ epoch interruption | 1e8 fuel / 调用 |
| 墙钟 | 调用级 timeout，超时 kill store | 10s |
| 内存 | Store limiter（memory growing limit） | 64 MiB |
| 输出 | 返回值 + stdout 截断 | 1 MiB |
| 并发 | per-user / per-agent 并发槽 | 2 |

### I/O 模型：宿主函数中介

- **文件系统**：不挂载任何宿主目录。提供内存 FS（一次性输入文件写入 + 结果读出），上限计入内存配额。
- **网络**：零默认。唯一出口是宿主函数 `http_fetch(url, opts)`：
  - per-agent 域名 allowlist（DIY 表单申请制，默认全拒）；
  - 仅 HTTPS；方法 GET/POST；请求/响应体大小上限；
  - 全量审计（时间、agent、URL、状态码、字节数）；
  - 每日配额（次数 + 字节）。
- **环境变量 / secrets**：不注入任何宿主环境。用户工具需要的凭据以显式参数传入（且默认脱敏审计）。

### 语言支持

| 语言 | 路径 | 约束 |
|---|---|---|
| JS / TS（主推） | 编译 `wasm32-wasi`（如 `jco` / Componentize-JS） | 无特别限制；`http_fetch` 经宿主 |
| Python | Pyodide（wasm32-unknown-emscripten，sidecar 内 Node 驱动） | 无 threading/multiprocessing/sockets；ssl 为 stub；包 = Pyodide 内置 + 纯 wheel（micropip）；网络仍经宿主函数 |

Python 侧产品能力边界以此为准：**"数据变换/计算"型工具，非"任意 Python 生态"**。requests 可用但受 CORS 级限制（一律引导走 `http_fetch`）。

### 备选方案与否决理由

| 备选 | 否决理由 |
|---|---|
| Pyodide 嵌入 FastAPI 进程（asyncio/线程内直接跑） | DEF CON 34 已证伪：单实例内存可被同进程代码读写；Python 执行不受限；一个漏洞打穿业务面 |
| 普通 Docker 容器执行 | 共享内核不是安全边界（runc CVE 记录）；冷启动与镜像管理成本高 |
| E2B / Modal 等托管沙箱 | 数据出境与自建要求冲突；后期可作 microVM 升级选项，非本期 |
| Firecracker microVM 自建 | 隔离最强但运维成本最高；当前威胁模型下 WASM+进程隔离已足够；留作演进方向 |

## 验收标准（M1）

恶意样本全绿才算沙箱基线成立：

1. `while True: pass` → fuel 耗尽中断，返回结构化错误，sidecar 存活。
2. 内存炸弹（大列表/大文件）→ limiter 触发，OOM 处理为可读错误。
3. 尝试 `open('/etc/passwd')` / `os.system` / socket → 不可用或被拒。
4. `http_fetch('http://evil.example.com')` → allowlist 外拒 + 审计记录。
5. 输出洪水（print 100MB）→ 截断到上限。
6. 两次调用之间状态不泄漏（A 调用写的文件 B 调用不可见）。
7. sidecar 被 kill 后自动重启，进行中的调用返回明确错误而非挂起。

## 参考实现锚点

- Wasmtime fuel/epoch/limiter：wasmtime-py `Store.set_fuel` / `set_epoch_deadline` / `limiter`。
- Pyodide：Node 内 `loadPyodide`，`setStdout`/`setStderr` 截断，`pyodide.http` 禁用，`runPythonAsync` + 外部 watchdog。
- 审计日志结构：`{ts, agent_id, tool, lang, fuel_used, wall_ms, urls[], verdict}`。
