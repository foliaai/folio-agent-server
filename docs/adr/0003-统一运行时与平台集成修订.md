# ADR-0003: 统一单运行时与平台集成修订

> 状态：**已接受**（2026-09）
> 上游文档：`docs/智能体平台架构方案.md`（v2）
> 撤销：ADR-0002 的 **D2**（DIY 运行时 = Pydantic AI AgentSpec）与 **D3**（双运行时共存纪律）

## 背景

v1 方案（主方案 v1 + ADR-0002）评审发现四个问题：

1. **双运行时必要性论证不足**。调研横评数据显示 Pydantic AI 2.0 相对 OpenAI Agents SDK 无不可替代优势（input tokens 1,338 vs 1,352；中位延迟 2.2s vs 2.5s，Pydantic AI 略优但同档）；v1 只列了 SDK 的优点（这些优点 Pydantic AI 基本都有），未论证其不可替代性。双运行时的真实成本是两套依赖升级、两套观测、两套流式/工具适配——对个人项目，这笔"受控架构债"的利息过高。
2. **技能层与现有生态脱节**。v1 §5 只提"AKS 技能格式一次性迁移脚本"，归属错误——现有技能体系的数据主人是 **skill_service**（唯一写入口，MySQL + MinIO），AKS 只是 HTTP 只读消费者。若 agent_apps 自建技能存储，将成为第三套技能数据源。
3. **部署拓扑缺失**。前端单一 `NEXT_PUBLIC_API_URL` 指向 :8000（AKS），但 document-compliance 等路由在 agent_apps；agent_apps `main.py` 默认端口 8001 与 skill_service 冲突；Next.js rewrites 不能可靠代理 WebSocket。
4. **subagent 扇出无成本护栏**。方案自引"多 agent 15× token"证据，却未给扇出任何约束，风险清单 5 条里没有"扇出失控"。

## 决策

### D1 DIY 运行时：撤销 Pydantic AI，统一为 OpenAI Agents SDK + 自研 AgentSpec 薄层

Pydantic AI AgentSpec 提供的能力，全部可由薄层 + SDK 覆盖：

| Pydantic AI 卖点 | SDK + 薄层替代 | 成本 |
|---|---|---|
| YAML spec + `from_spec()` | 自研 `AgentSpec`（Pydantic 模型）+ Agent 工厂（`src/diy/compile.py`） | ~200 行 |
| `to_file(schema_path)` 出 JSON Schema | `AgentSpec.model_json_schema()`（Pydantic 原生） | 0 |
| `deps_schema` 构造期模板校验 | validator 校验 `instructions` 的 `{{var}}` ⊆ `deps_schema.properties` | ~50 行 |
| `output_schema` 结构化输出 | SDK `output_type`——**运行时强校验 + 自动重试，强于 Pydantic AI**（后者是给模型的指令，不校验） | 0 |
| token/请求预算硬上限 | 自研 `BudgetLedger`（首页 loop 也需要，一份代码两处复用） | ~150 行 |
| agent-as-tool / 流式 | SDK 原生 | 0 |

净收益：一套依赖升级、一套观测、一套工具适配；ADR-0002 D3 的五条纪律整套失效删除；v1 风险清单中"`output_schema` 不做运行时校验"一条消失。

**保留 Pydantic AI 的唯一场景**：未来需要 durable execution / checkpoint 长流程时按需引入（主方案 §9 非目标第 5 条）。届时迁移面小——AgentSpec 是平台自有格式。

### D2 单运行时纪律（取代 ADR-0002 D3）

四条纪律继续有效，主语从"两个运行时"改为"两个场景"（首页 loop / DIY）：

1. 工具层只经 MCP：两个场景都不直接实现工具，都只做 MCP client。
2. agent 定义收敛到声明式 AgentSpec：首页 agent 的配置同样以 AgentSpec 同构结构持久化。
3. 模型路由唯一：同一 LiteLLM proxy，同一份模型清单。
4. 技能层唯一：skill-service + SKILL.md，共用加载逻辑（见 D3）。

原第 5 条（每季度评估是否合并双运行时）删除——已合并。

### D3 技能层归属：skill-service 唯一持有者，SKILL.md 下沉 skill_core

- SKILL.md 解析（frontmatter、Level 0/1/2 渐进披露）实现于 skill_core——它本就是为多后端复用设计的。
- skill_service 升级为 SKILL.md 的持有者；AKS 既有技能经一次性迁移脚本转为 SKILL.md 存回 skill_service。
- agent_apps 复用 AKS 的 `SkillServiceRepository` 模式（HTTP 只读，约 200 行），`SKILL_SERVICE_URL` 指向同一实例。
- **分发方式修正**：废弃 `third_party/` wheel 手动拷贝（AKS 内已堆 0.2.1/0.2.2/0.2.3 三个版本，漂移已发生），改为 uv path（本地）/ git tag（部署）引用。

### D4 统一网关与端口约定

- Caddy 统一网关：本地 :4000 / 生产 :443；`/api/chat/*`、`/api/knowledge/*` → AKS；`/api/v1/*` → agent_apps；`/skill-api/*` → skill_service。
- 端口约定固化：AKS 8000、skill_service 8001、**agent_apps 8002（`main.py` 默认值从 8001 修改）**。
- 前端删 `next.config.mjs` 的 `/skill-api` rewrite，只留一个 `NEXT_PUBLIC_API_URL` 指向网关。
- 鉴权在各后端本地校验 Logto JWT，网关只透传。
- WS 信封协议以 AKS 现有帧协议为基线升格为平台协议，agent_apps 只增不改（新增 `subagent.*`、`budget.*` 帧）。

### D5 subagent 成本护栏：BudgetLedger

三层限制（结构层防扇出失控 / 预算层防烧钱 / 行为层防过度触发）+ 熔断（80% 收敛、100% 拒绝并收尾）+ 降级优先于失败 + 扇出记录可观测。参数与默认值见主方案 §7。

## 后果

**正面**：消除双运行时漂移风险与双份维护成本；技能层与既有生态（前端 /skills 页、AKS @skill）天然一致；部署拓扑从三处混乱收敛为单入口；扇出烧钱风险有硬约束。

**负面/代价**：自研薄层 ~400 行的维护面（换取的是删掉一整个框架依赖）；单运行时把 SDK 0.x churn 风险集中（缓解：MCP 层保运行时可替换性，业务逻辑不侵入 SDK）；skill_core 需要 SKILL.md 能力的一次开发投入。
