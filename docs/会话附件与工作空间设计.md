## 1. 背景与目标

首页通用智能体（agent-server :8002）目前不支持上传附件。本设计补齐两类能力：

- **文件上传**：文档类文件（PDF/docx/pptx 等）经 MinerU 解析为 Markdown 供 LLM 阅读；
  数据类文件（CSV/JSON/代码等）保留原始文件，走沙箱 code_execute 分析。
- **图片上传**：图片存入会话工作空间，主模型按需理解图片内容。
- 两类附件统一挂在 **session 工作空间** 内，生命周期跟会话走。

## 3. 工作空间（Session Workspace）

**职责边界（D5）**：session 工作空间是会话级容器，只装两类内容——用户上传的
文件、agent 执行过程产生的文件。**长期记忆（memory）跟随用户、跨会话存活，
不放在会话工作空间**，作为独立的 user 级存储后续单独立项；本期仅在工具面
预留 `memory_read / memory_write` 接口位，不实现。

### 3.1 存储

- **对象存储**（MinIO，D17：同实例**新桶** `agent-workspace`——dev 共用
  localhost:9000、JP/prd 共用 milvus-minio 实例；与 AKS 桶隔离，配额/清理/误删
  互不影响）：
  - 原始文件：`agent-workspace/{user_id}/{session_id}/{file_id}`
  - 解析产物 markdown：`agent-workspace/{user_id}/{session_id}/{file_id}.md`
  - MinerU 抽出图片资产：`agent-workspace/{user_id}/{session_id}/{file_id}.assets/{image_name}`
    （与 AKS 的 `parsed/{file_id}/images/` 同构，D14，详见 §4.4）
- **元数据**（MySQL 新表 `agent_session_file`，与 agent_session 同构）：
  `id / user_id / session_id / kind(file|image) / origin(upload|agent) / name / mime / size /
  parse_status(pending|parsing|ready|failed) / parse_error / md_object_key /
  created_at`。
- **`origin` 的用途（D6）**：不是存储位置，是目录里的"来源"标签，让同一容器
  对不同来源执行不同策略——清理（upload 保守保留、agent 产物可激进清理）、
  配额（upload 宽松、agent 严格，防代码失控写文件）、展示（附件 chip vs
  生成产物列表）。
- **权限**：复用 `_owned_or_404` 模式（session 属主 = file 属主），所有访问校验。

### 3.2 生命周期

- 软删会话 → `origin=upload` 附件保留（可恢复）；`origin=agent` 产物保留但
  可随定期任务更早回收（派生物，可再生）；物理清理见 §3.4（D9）。
- 切换会话工作空间不跟随（天然隔离）；附件不进知识库、不做索引。

### 3.3 沙箱读写闭环（文件分型的关键 + 执行产物落盘）

原始文件必须保留在工作空间——"上传 Excel 让 agent 分析"的正解是
code_execute 读原始文件，而非 MinerU 转出来的 markdown。沙箱按 ADR-0001
保持零宿主文件系统，通过**显式通道**形成读写闭环（非开放 FS）：

- **读挂载**：调用开始时，把该会话 workspace 的文件预载进本次调用的内存 FS
  （文件数/大小受配额约束），代码直接 `open()` 读；
- **写回（drain）**：调用结束时，宿主把内存 FS 中新增/变更的文件序列化回
  workspace（`origin=agent`），工具结果只返回文件存根列表，大产物不进 LLM
  上下文、不进 WS 帧；
- **配额**：写回前校验单文件大小、单次文件数、workspace 总量（per-session
  配额），超限拒绝并返回可读错误；
- 产物经 `GET /files/{fid}/raw` 供用户下载。

**闭环语义（D8，2026-10-08 拍板）**：

- **方向区分**：进口（预载）已有现成通道——`SandboxRequest.files`
  （contracts.py，base64 内存 FS 输入文件）；缺的只是出口：
  `SandboxResult` 扩 `files_out` 字段，sidecar 在执行结束、内存 FS 销毁前
  对新增/变更文件做差异快照序列化回传，API 侧写入 workspace
  （`origin=agent`）。**出口的存在理由**：代码生成的文件（图表 / 导出
  CSV / 报告）只存在于单次调用的内存 FS 里，调用一结束就蒸发——没有
  出口，用户永远拿不到这些产物，后续轮次的模型也无法引用。
- **上传文件在沙箱内只读**：预载文件以只读方式挂入内存 FS，agent 代码
  不可覆写用户上传；重名写入直接报错（提示模型换文件名），不做自动改名的
  静默覆盖。
- **配额全部在 API 侧执行**，理由有三：① 会话级累计配额（总量）跨多次
  调用累计，而 sidecar 每次调用都是无状态新实例，看不到历史；② 落盘动作
  （put_object + 写目录行）本来就发生在 API 进程，配额是落盘前的守门，
  sidecar 既无 MinIO 也无 MySQL 客户端；③ ADR-0001 信任边界——sidecar 是
  薄执行器，只保留引擎必须本地执行的硬限制（fuel/内存/墙钟），业务策略
  越少越好（现有 limits 同样是 API 钳制后下发的风格）。

**参数集（config 新段 `[sandbox.workspace]`，默认值为首版建议、实现期可调）**：

| 参数 | 默认值 | 说明 |
|---|---|---|
| 预载单次文件数 | 20 | 超出跳过并在工具结果中说明 |
| 预载总量 | 32MB | 计入 memory_limit_mb，钳制规则=不超过内存配额的 50% |
| 预载范围 | 全部 kind=file（含 .md 解析产物），不含图片 | 代码分析用不上图片二进制 |
| 写回单次文件数 | 10 | 防目录轰炸 |
| 写回单文件上限 | 10MB | |
| 写回单次总量 | 20MB | 防代码失控刷 MinIO |
| 会话 workspace 总量 | 500MB（agent 产物子配额 200MB） | 写回前校验，超限拒绝并返回可读错误，**不静默淘汰** |

首期实现顺序：先落上传链路与 `read_workspace_file` 工具直读；读写闭环
（预载 + drain）随后补齐。

### 3.4 物理清理（定期任务，D9）

- **触发**：进程内 APScheduler（挂 FastAPI lifespan，单实例模式），每日
  03:00 执行，单批最多清 500 个对象防 IO 突刺；
- **upload 级（保守）**：软删会话 > 30 天 → 硬删（MinIO 对象 + 目录行）；
  活跃会话的上传永不自动清理；解析失败 > 7 天的目录行自动清；
- **agent 级**：活跃会话**不做年龄淘汰**——产物可能是用户要的交付物，
  只在写入点以配额拒绝（§3.3）；软删会话 > 7 天 → 硬删 agent 产物
  （派生物，比 upload 激进）；
- **临时区孤儿回收（D11）**：D1 的 `POST /uploads` 临时区上传 24 小时内
  未绑定会话即清（对象 + 行），补齐本节此前只覆盖会话内文件的空档；
- **写序防孤儿**：先写目录行（status=pending）再写 MinIO 对象——悬空行
  指向不存在的对象是自愈型（清理时 delete-if-exists），反序会产生对账
  扫不出来的孤儿对象；孤儿对象对账扫描不做，记将来项；
- 留存键直接用 BaseModel 现有 `deleted` / `update_time` 列，**零新增 schema**。

## 4. 文件链路

### 4.1 类型路由（上传时按 mime/扩展名分流）

| 类型 | 路由 | 说明 |
|---|---|---|
| PDF / docx / pptx | MinerU → markdown | LLM 阅读投影；MinerU 抽出的图片存 MinIO，markdown 内引用 |
| md / txt | 直接存为 markdown | 不经 MinerU |
| CSV / JSON / xlsx / 代码等 | 仅存原始文件 | `read_workspace_file` 直读；分析场景交 code_execute（D19：xlsx 明确归此档） |
| 图片 | 见 §5 | |

### 4.2 异步解析（不做同步接口）

MinerU 是分钟级耗时，同步 HTTP 会在网关/ frp 后超时：

1. `POST .../files` 上传即返回 `file_id`（status=pending→parsing）；
2. 后台任务提交 MinerU（client 采用 AKS `Mineru2Client` 同款"任务队列+轮询"模式，
   agent-server 自持一份，直连共用实例，D3）；
3. 前端轮询文件状态（轻量，复用知识库上传卡片的交互模式）；
4. 完成 → ready；失败 → failed（error 可见，可删除重传；D21：**不自动重试**，
   用户手动重传）。

### 4.3 Markdown 进上下文：存根 + 按需读

- 注入 agent 上下文的是**文件存根**：文件名、类型、大小、字数、开头摘要（前几百字）；
  存根只在附件绑定到达的**首轮注入一次**，不每轮重复（D18）；
- 新增工具 `read_workspace_file(file_id, section?)` 按需拉全文/分节；分节两种模式
  （D13）：按 markdown 标题分节 + 按行号窗口（长文翻页读）。不把全文塞进首条消息
  （防上下文烧穿，与工具面哲学一致）；
- **workspace 发现三层（D18）**：① 首轮一次性存根注入；② 沙箱内自查——预载后
  `os.listdir()` 天然可见（Pyodide 里列目录的等价物，WASM 无 shell，os.listdir
  即"执行命令看目录"的等价物）；③ `list_workspace_files()` 工具作为
  名称 → file_id 的权威映射来源（尤其 agent 产物中途出现后刷新清单）。
  工具 description 保持静态，不做每轮动态注入——对齐主流做法（OpenAI 上传时
  注入一次性清单，Claude Code 靠 LS 类工具自查）。

### 4.4 MinerU 产物与图片资产（D14）

MinerU 任务数据自带**现成 markdown 文本**（`markdown.content`）+ images base64
字典——不需要从 content_list 重建（那是 AKS 索引管线为分块消费的结构化形态，
我们不做索引）。"重建"工作收敛为一个小函数：

1. 解析完成时遍历 images 字典，逐张上传到 `{file_id}.assets/{image_name}`；
2. 把 md 内的相对图片引用统一重写为 `assets/{image_name}` 后落盘；
3. 相对引用对 LLM 也最干净——模型看到 `assets/fig1.jpg` 即知有图，不需要真 URL；
4. 前端渲染时的图片访问：渲染 md 前先调 `POST /files/{fid}/asset-urls` 批量换
   MinIO presigned URL（短 TTL），替换相对引用后渲染——与 AKS 聊天图片 chunk
   的"按需换 presigned"同款（chunk.py 模式）。**浏览器直连 MinIO 的可达性是
   AKS 三环境已跑通的事实，抄同款即继承，零新增验证**（与 D7 否掉 presigned
   传**给模型**不冲突：一个是 ModelNexus 服务端出口回源，一个是用户浏览器）。

## 5. 图片链路（双路）

- **判定**：registry 的 `supports_multimodal` 能力标记。model_lake 路径已由
  `/v1/models` 富元数据**运行时自动合成**（`registry._fetch_model_lake` 读
  `architecture.input_modalities` 回写白名单；2026-10-08 已在本地 8002 实测，
  deepseek-v4.1-flash / kimi-k3 / qwen3.5-flash 等均已返回
  `supports_multimodal: true`）。`multimodal_models.json` 仅 litellm 旧模式的
  遗留白名单，不需要补。残留小尾巴：`registry.py` 字段描述仍写"来自
  config/multimodal_models.json 白名单"（litellm 专属措辞），实现期顺手修正。
- **路线 A（主模型支持视觉）**：图片以 OpenAI `image_url` content part
  直接进消息，模型原生看图。**多轮寿命（D12）**：image part 只进首轮消息，
  不随每轮上下文重发整段 base64；后续轮次模型凭存根用 `understand_image`
  按需再看（该工具两条路线都可用）。
- **路线 B（不支持，默认路径）**：挂工具 `understand_image(file_id, question?)`，
  内部调 `[presets.multimodal]` 设定的 VLM（D4），图片 + 问题 → 文字描述返回；
  config 增 `multimodal_model_preset = "multimodal"` 引用键（照抄 AKS 模式）。
- **图片传递**：**固定 base64（D7，2026-10-08 拍板）**，上传时压缩
  （长边 2048 / JPEG q85，单图约 300-500KB）。presigned URL 方案已评估并
  关闭：ModelNexus 推理出口无法回源内网 MinIO（dev=localhost、JP/prd 均为
  内网 201.14 地址，跨网不可达），为传图开公网暴露面不值得；与 AKS 现行
  base64 先例一致（`image_processing.py` 的 data URL）。

## 6. API 与协议扩展

### 6.1 REST（前缀 /api/v1）

```
POST /sessions/{sid}/files        multipart 上传 → 202 {file_id, kind, parse_status}
GET  /sessions/{sid}/files        附件列表（含解析状态，供轮询）
GET  /files/{fid}                 元数据
GET  /files/{fid}/raw             原始文件流（鉴权后）
GET  /files/{fid}/markdown        解析产物（文档类）
DELETE /files/{fid}               删除
POST /files/{fid}/asset-urls      批量换 MinIO presigned URL（md 内图片渲染用，D14）
POST /uploads                     临时区上传（会话未创建时，D1）→ {file_id}
       （首次发送时随 start 帧绑定到新 session，服务端搬运归位）
```

**上传硬限制（D10）**：单文件 ≤ 50MB；单会话附件 ≤ 20 个；拒可执行文件
（exe/dll/so 等）；mime 嗅探防伪装（按内容判定，不只看扩展名）。

### 6.2 WS 帧

- C→S `start` 帧扩展：`attachments: [{file_id, kind}]`（现有字段
  `{message, model?, session_id?}` 不动）。
- S→C **不新增文件状态帧**：纯轮询（D15，推送选项移除）。
- **附件持久化（D16）**：user message 的 items 存 `{file_id, kind, 存根快照}`，
  历史重放（Mongo 装配上下文 / 前端回放）零查库。

### 6.3 发送锁定（D2）

- 任一附件 parse_status 非 ready → 前端发送按钮锁定并显示原因；
- 服务端在 start 帧收到非 ready 附件时同样拒绝（防绕过）。

## 7. 前端（folio-web）

- composer 加附件按钮（回形针）+ 附件 chip 状态机：
  上传中 → 解析中(spinner) → 就绪 / 失败(可重传可删)；
