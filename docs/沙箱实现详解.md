## 0. 这个沙箱解决什么问题

智能体平台要执行两类**不可信代码**：

1. 用户在 DIY 智能体里写的工具（Python / JS）；
2. LLM 生成的代码（首页 agent 的 `code_execute` 工具）。

"不可信"意味着这些代码可能是恶意的：死循环烧 CPU、分配大内存、读宿主文件系统（`/etc/passwd`）、对外发请求偷数据。沙箱的职责是让这些代码**能跑，但跑不出任何边界**：

```
能做的：纯计算、读"本次调用携带的"输入文件、经检查的 HTTPS 请求（唯一出口 folio_fetch）
不能做的：碰宿主文件系统、直连网络、无限 CPU/内存、跨调用留状态、拖死服务本身
```

一句话理解架构：**不给代码一个操作系统，只给一个函数运行环境**。这是它与容器沙箱（给一个完整 Linux）的本质区别，也是隔离强度的来源。

## 1. 三分钟看懂：一次调用的完整旅程

以「用 Python 算个总和」为例，数据从进到出经过这些环节：

```
你的业务代码（未来的 tools/builtin/code_execute.py）
  │
  │  await get_sandbox_client().execute(lang=PYTHON, code="result = 1+2", meta={...})
  ▼
client.py  SandboxClient.execute()
  │  ① 组装 SandboxRequest：生成请求 id、limits 钳制（clamp_limits：只能收紧不能放宽）
  │  ② 计算外层超时 = 引擎墙钟 + Node 孙进程缓冲 + 10s 协议余量
  ▼
manager.py SidecarManager.acquire()
  │  ③ 轮询找一个"活着且不忙"的 sidecar 进程（单飞：一个 sidecar 同时只跑一个请求）
  ▼
manager.py SidecarProcess.execute()
  │  ④ 把请求序列化成一行 JSON（加 "type":"exec"），写进 sidecar 的 stdin
  │  ⑤ await 一个 Future——谁来唤醒它？sidecar 的读循环（第 ⑧ 步）
  ▼
════════════ 进程边界（stdin/stdout 管道，行分隔 JSON 协议）════════════
  ▼
sidecar/server.py（进程 B 主循环）
  │  ⑥ 读到 exec 帧 → engines.dispatch() 按语言分发 → PyodideEngine.execute()
  │     （JS 语言则去 WasmtimeEngine，见 §3.2.3）
  ▼
pyodide_engine.py _run()
  │  ⑦ spawn 一个全新的 Node 子进程跑 runner.js（进程 C，每请求一个，用完即弃）
  │     等 ready 帧 → 发 run 帧 → 进入读循环
  ▼
════════════ 进程边界（又一个 stdin/stdout）════════════
  ▼
runner.js（进程 C）
  │  ⑧ 把输入文件写进内存 FS → runPythonAsync(code) → 读回 result 变量
  │     （用户代码里调 folio_fetch 时：写一帧 {"type":"net",...} 回进程 B 请求代理）
  │  ⑨ 发 done 帧 {ok, stdout, result, ...} → exit(0)
  ▼
pyodide_engine 收到 done → 组装 SandboxResult 返回
  ▲
  │  ⑩ server.py 把 result 包成 SandboxResponse（type=result）写 stdout
  │  ⑪ manager 的读循环收到这帧 → 按 id 找到第 ⑤ 步的 Future → set_result 唤醒
  ▼
client.py  ⑫ audit.py 落审计（fuel/时长/verdict/网络访问记录）→ 返回 SandboxResult
```

**JS 路径的差别**只在第 ⑦ 步之后：不走 Node，而是 Wasmtime 直接在进程 B 内编译执行 wasm 组件（但这仍是"进程隔离"——wasm 跑在 sidecar 里，不碰 API 服务器）。

**如果用户代码里调了 `folio_fetch("https://api.example.com")`**：

```
Python 代码: from js import folio_fetch; await folio_fetch(url)
  → runner.js 里注入的 JS 函数（globalThis.folio_fetch）
    → 写 {"type":"net","seq":N,"url":...} 到自己的 stdout（进程 C→B）
  → pyodide_engine 读循环收到 → 调 hostfuncs.HostContext.http_fetch(url,...)
    → allowlist 检查（进程 B，不可信代码碰不到这层逻辑）
    → 真实 HTTP 请求也是这里发的（进程 B，宿主侧）
    → 结果 {"type":"net-result","seq":N,...} 写回进程 C 的 stdin
  → runner.js 的 pending Map 按 seq 匹配 → resolve Promise → Python 拿到结果
```

关键点：**allowlist 检查永远发生在不可信代码所在进程之外**。用户代码即使被攻破也无法伪造或绕过检查——它只能"请求"，不能"执行"。

## 2. 进程拓扑：为什么是三个进程

```
进程 A  API 服务器（FastAPI :8002，你日常启动的就是它）
进程 B  sidecar × N（python -m src.sandbox.sidecar，低权限运行，池化管理）
进程 C  node runner.js × 请求数（Pyodide 运行时，每请求一个，秒级生灭）
```

| 边界 | 隔离手段 | 防什么 |
|---|---|---|
| A ↔ B | OS 进程边界 + stdin/stdout 管道 | wasm 引擎被攻破时摸不到业务进程（ADR 红线） |
| B ↔ C | 又一层 OS 进程 | Pyodide（DEF CON 34 打穿七个产品的那个）与 sidecar 管理逻辑隔离 |
| 代码 ↔ 机器 | Wasmtime 线性内存 / Pyodide wasm 堆 | 代码根本"看不到"宿主的文件系统、网络、环境变量 |

**为什么 Pyodide 要单独再隔一层（进程 C）？** Pyodide 的官方安全模型是"输入代码可信"——它跑在哪个进程，哪个进程的内存就等于裸奔。ADR-0001 的红线"绝不把 Pyodide 嵌入 API 服务器进程"就是这个原因；多一层进程边界的成本（~1s 冷启动）换来的是 sidecar 管理逻辑（协议循环、selfdestruct 判定）不被用户代码同进程污染。

**为什么 JS 不需要进程 C？** Wasmtime 的线性内存边界本身就是硬边界（代码无法表达"越界访问"），进程 B 内执行即可；Pyodide 则是"代码与运行时共享内存"，必须再隔。

## 3. 文件地图：每个文件是干什么的

### 3.1 API 服务器侧（进程 A 使用的代码）

#### `src/sandbox/contracts.py` —— 协议契约（最重要的一个文件）

**双端共享的数据定义**，进程 A 和进程 B 都 import 它，保证两边对"帧长什么样"的理解永远一致。

- `SandboxLang`：语言枚举（`js` / `python`），决定引擎分发
- `SandboxErrorCode`：十种错误码。这是**稳定性契约**——它是 API 侧、前端、审计日志共同依赖的词表，改值等于破坏兼容（unit 测试锁定了每个值）
- `SandboxLimits`：单次调用的资源限制（fuel/墙钟/内存/输出/网络配额/Node 超时）
- `SandboxRequest` / `SandboxResponse`：exec 帧 / result 帧的完整结构。注意 `SandboxResponse.type` 字段——sidecar 输出的每一行 JSON 都带 type 标记，读循环靠它分发
- `NetEvent`：一次网络访问的记录（url/是否放行/状态码/字节数/拒绝原因），**由 sidecar 回传、API 侧落审计**——这样 sidecar 进程本身不需要任何文件写权限
- `decode_exec_frame()`：容错解析（坏帧返回 None 而非抛异常——协议边界不允许意外炸掉读循环）

**学习建议**：读懂这个文件，整个系统的"接口"就懂了。

#### `src/sandbox/limits.py` —— 限制的钳制规则

两层结构：**平台默认**（config.toml `[sandbox]` 段 → `limits_from_config()`）和**代码级硬顶**（`HARD_CEILINGS`，写死在代码里，配置文件被改大也无效——最后一道保险）。

`clamp_limits(requested, platform)` 的规则：请求值缺失用平台默认；显式给的值**只能比平台默认更严**（更大的请求被悄悄压回默认，不报错——DIY 表单允许填小不许填大）。

#### `src/sandbox/allowlist.py` —— 域名白名单 + SSRF 防护

`check_url(url, allowlist)` 的检查顺序（顺序本身就是设计）：

1. URL 能否解析（`bad_url`）
2. scheme 必须 https（`scheme_not_https`）
3. 端口必须默认 443（`port_not_allowed`）
4. **IP 字面量一律拒**（`ip_literal_denied`）——allowlist 是域名制，写 IP 等于绕过域名的意义
5. localhost/私网段拒（`private_host`）
6. allowlist 匹配：`example.com` 语义 = 该域**及其所有子域**；空 allowlist = 全拒

`resolve_and_check(hostname, allowlist)`：**DNS 解析后的二次检查**。为什么需要？攻击者可以把自己控制的域名解析到 `192.168.x.x`（DNS rebinding）——第一次检查看到的是合法域名，真实连接时却打向内网。所以 hostfuncs 在真正发请求前用解析出的 IP 再查一次私网。

#### `src/sandbox/audit.py` —— 审计落盘

只做两件事：`log_execution()`（每次调用的完整记录）和 `log_sidecar_event()`（进程池事件如 respawn）。记录结构对齐 ADR-0001：`{ts, agent_id, user_id, tool, lang, fuel_used, wall_ms, verdict, urls[]}`。按天写 `SANDBOX_AUDIT_DIR/YYYY-MM-DD.jsonl`。落盘失败不抛——审计不能影响业务链路，但会留 ERROR 日志。

#### `src/sandbox/client.py` —— 业务侧唯一入口

`SandboxClient.execute(lang, code, input, files, allowlist, limits, meta)` 是**未来所有调用方（工具层/agent loop）唯一应该用的函数**。它负责：组装请求（uuid 短 id）→ 钳制 → 池化执行 → **异常归一化**（`SidecarCrashedError`/`TimeoutError` 都变成带错误码的 `SandboxResult`，调用方永远拿到统一类型，不会收到意外异常）→ 审计。

模块级 `start_sandbox()` / `stop_sandbox()` 由 main.py 的 lifespan 调用；`get_sandbox_client()` 在没启动时抛 RuntimeError（fail fast，防止静默用错）。

#### `src/sandbox/manager.py` —— 进程池

三个角色：

- **`SidecarProcess`**：一个 sidecar 实例的完整生命周期。`start()` spawn 进程并等 ready 帧（30s 超时）；`execute()` 发帧 + 挂 Future 等 result；`_read_loop()` 是常驻协程——读到 result 帧就按 id 唤醒对应 Future，读到 EOF（进程死了）就把所有 pending Future 设为 `SidecarCrashedError`。`lock`（asyncio.Lock）实现**单飞**：一个 sidecar 同时只处理一个请求
- **`SidecarManager`**：N 个槽位的池。`acquire()` 轮询找一个不忙的实例；`_on_death()` 在实例死亡后延迟 0.5s 自动重生（延迟是为了防 crash-loop 打满 CPU）
- 读流的 `limit=32MB` 不是可选项——asyncio 的 StreamReader 默认 64KB 行上限，1MB+ 的 result 帧会触发 `LimitOverrunError`，曾把大输出请求误判成"进程死亡"（§6 坑 5）

### 3.2 sidecar 侧（进程 B）

#### `src/sandbox/sidecar/__main__.py` —— 入口

三行逻辑：探测可用引擎（wasmtime 恒可用；python 要看 node 和 node_modules/pyodide 在不在）→ 输出 ready 帧 → 进入 server 循环。部署要求低权限用户运行（无 home、无 shell）。

#### `src/sandbox/sidecar/server.py` —— 协议主循环

M1 是**串行**模型：一次处理一个请求（并发靠进程池横向扩，不靠单进程并发——简单且无共享状态问题）。读 stdin 每行 → ping 回 pong / exec 交给引擎 → 结果包成 result 帧写回。**stdout 是协议通道**，所以 sidecar 里所有日志（loguru）都写 stderr——这是为什么 manager 把子进程的 stderr 单独 PIPE 走。

执行完的成败交给 `SelfDestructTracker` 记账（见 selfdestruct.py）。

#### `src/sandbox/sidecar/engines/__init__.py` —— 引擎分发

`dispatch(request)` 按 `request.lang` 懒初始化并调用对应引擎；`available_engines()` 供启动探测。引擎不可用时返回 ENGINE_CRASH 带说明（而不是让 sidecar 崩）。

#### `src/sandbox/sidecar/engines/base.py` —— 引擎基类

模板方法模式：子类只实现 `_run()`，基类的 `execute()` 统一做三件事——**异常收敛**（任何异常都变成错误码，引擎不允许把异常抛进协议层）、**计时**（wall_ms）、**输出截断**（`_truncate()`：stdout/stderr/result 按 UTF-8 字节计超限截断 + 追加 `[folio-sandbox: output truncated]` 标记 + 置 OUTPUT_TRUNCATED 错误码但保持 ok=True）。

**两个引擎共用同一段截断代码**——这就是为什么 unit 测试直接测 `_truncate` 就能覆盖 JS 路径。

#### `src/sandbox/sidecar/engines/wasmtime_engine.py` —— JS 引擎（最难的一个文件）

执行用户 JS 的路径是：**用户 JS 先离线编译成 wasm 组件**（tools/wasm，见 §3.4），运行时这里只做"加载 + 调用"。`_run()` 的步骤：

1. base64 解码 → `wcomp.Component(engine, bytes)` 编译（带缓存：相同 wasm 字节复用 Component 对象）
2. `wasmtime.Store`：`set_fuel(限额)` + `set_limits(memory_size=...)`——**每请求全新 Store**，这是跨调用状态隔离的根源
3. `set_epoch_deadline(1)` + 起一个 `threading.Timer` 到点 `engine.increment_epoch()`——**墙钟超时的实现机制**：epoch 是 wasmtime 官方的中断机制，到点 wasm 执行会收到干净的 trap（"epoch deadline reached"），比 kill 进程温和
4. Linker 装配：`add_wasip2()`（JS 运行时需要的基础 WASI）+ `add_wasi_http()`（Componentize-JS 的 fetch 语义映射引入）+ **注册 folio 宿主函数**
5. `instance.get_func(store, "run")` → `run(store, input)` → 拿返回字符串

**必须知道的四个坑**（都写在代码注释和 §6）：

- `store.set_wasi(WasiConfig())` + `store.set_wasi_http()` 是**硬性要求**——C API 的 WASI 宿主实现要从 Store 里取状态，缺了会在用户代码碰到 wasi:clocks 时**直接 Rust panic**（比如 `Date.now()`）
- linker 的 `root().add_instance()` 返回的句柄会**锁住** linker，必须 `with` 作用域销毁后才能 `instantiate`
- 宿主函数的 Python 签名是 `func(store, url, body, ct)`——**第一个参数永远是 store context**
- import 的 interface 名是**全名严格匹配**，我们的 WIT 刻意不带版本号（`folio:sandbox/host`）

宿主函数的实现是 `_http_fetch_json` / `_read_file_json`：把 HostContext 的返回包装成 JSON 字符串。**为什么协议全用 string？** wasmtime-py 对 option/result 等 WIT 复合类型的 Python 编解码支持不完整，string 最稳——复合语义（状态码、错误）用 JSON 承载，TS 侧解析（见 runner.wit 注释）。

#### `src/sandbox/sidecar/engines/pyodide_engine.py` —— Python 引擎

**每请求 spawn 一个全新 Node 进程**（冷启动 ~1s，换来最强状态隔离——test_06 的验收就依赖这一点）。`_run()` 流程：

1. spawn：`node --max-old-space-size=max(256, memory_limit_mb) runner.js`。两个细节：
   - Node 堆**独立计算**：Pyodide 运行时自身常驻 ~200MB，直接用 memory_limit_mb(64) 会误杀正常请求；Python 侧的真实内存限制靠 Linux 的 `RLIMIT_AS`（`_linux_address_space_limit`）+ wasm 堆编译期上限 2GB
   - `preexec_fn` 在 Linux 上设 RLIMIT_AS；macOS 上 setrlimit 是 no-op（开发机退化为墙钟兜底，生产是 Linux，语义完整）
2. 等 ready 帧 → 发 run 帧 → 进入**双职责读循环**：`net` 帧转给 HostContext 执行并回写 `net-result`（这就是 folio_fetch 的代理路径）；`done` 帧收尾
3. 墙钟 Timer 到点直接 `proc.kill()`——stdout 读循环随即 EOF，判定 TIMEOUT
4. stderr 用独立线程持续排空（防 Node 报错把管道塞满导致阻塞）

#### `src/sandbox/sidecar/hostfuncs.py` —— 宿主函数（唯一 I/O 通道）

`HostContext` 是**一次调用的宿主侧状态**：输入文件（内存 FS，请求结束即丢弃）、allowlist、限制、网络事件收集。所有用户代码的 I/O 请求都汇到这里执行：

- `http_fetch(url, body, content_type)`：五道检查（URL 解析→scheme/端口/IP/私网→allowlist→DNS 二次检查→配额与尺寸）→ `urllib` 发真实请求 → 响应按上限截断 → 每次都记 NetEvent（**包括被拒的**——审计要完整）
- 一个反直觉设计：HTTP 4xx/5xx 是"成功的网络访问"，状态码如实返回给用户代码；网络层异常才叫失败
- `read_file(name)`：basename 清洗后查内存 FS，非法路径/不存在抛 KeyError（引擎映射为错误）

#### `src/sandbox/sidecar/selfdestruct.py` —— 自杀监督

ADR-0001 的"sidecar 满足条件即自杀重启"的落地。**关键语义（开发中被测试纠正过）**：只有 `ENGINE_CRASH`（进程层异常）才计入连续失败；用户代码的业务错误（fuel 耗尽/超时/OOM/越权被拒）**不算**——那是对恶意/错误代码的正常响应，如果把它们也计数，一个高失败率的用户就能把整个池子打崩。致命错误立即自杀（`os._exit(3)` 跳过一切清理，最快让出资源），manager 负责重生。

#### `src/sandbox/sidecar/nodejs/runner.js` —— Pyodide 运行时（进程 C）

整个文件做四件事：

1. **加载与输出缓冲**：`loadPyodide({stdout/stderr: 截获回调})`——用户 print 的内容进缓冲区而非直接写 stdout（stdout 是协议通道！），超 `outputLimitBytes` 停止累计并留截断标记
2. **安全硬化**（用户代码执行前）：`globalThis.fetch/WebSocket/XMLHttpRequest` 全部替换成抛错函数；`delete globalThis.process`（防环境变量泄漏和 process.exit）；Python 侧 `sys.modules["pyodide.http"]` 换成抛错 stub。**为什么这么狠**：`from js import fetch` 在 Pyodide 里能直接拿到 JS 全局，node 25 又自带全局 fetch——不堵死这些，allowlist 就是摆设
3. **folio_fetch 注入**：`globalThis.folio_fetch = async (url, body, ct) => {...}`——写 net 帧到 stdout、把 Promise 挂进 pending Map、等 sidecar 的 net-result 回来 resolve。注意注入必须走 **globalThis**（`pyodide.globals.set` 写的是 Python 命名空间，`from js import` 看不到——踩过的坑）
4. **执行与结果**：输入文件写进 `/home/pydide`（内存 FS）+ chdir → `runPythonAsync(code)` → 再跑一小段固定代码读回 `result` 变量（**最后必须是函数调用表达式**，Pyodide 只返回 Expr 语句的值——if/else 复合语句返回 None，踩过）→ done 帧写出

**done 帧的写出有个关键细节**：`proc.stdout.write(payload, () => proc.exit(0))`——Node 的 pipe 写是异步的，直接 `exit` 会把没写完的大帧腰斩（2MB 的 done 帧曾经被截断到 JSON 解析失败，§6 坑 4）。

### 3.3 编译链（tools/wasm/，JS 工具的"构建工具"）

| 文件 | 作用 |
|---|---|
| `runner.wit` | **WIT 世界定义**——用户工具的"接口合同"。`world runner`：import 宿主的 `folio:sandbox/host`（http-fetch/read-file），export `run(input) -> string`。package 刻意不带版本号（带版本的 import 说明符解析有坑）。**协议全 string + JSON 承载语义**的设计约束写在注释里 |
| `build.ts` | 编译入口：`npx tsx build.ts samples/echo.js /tmp/echo.wasm`。用 Componentize-JS 把 JS 变成 wasm 组件（内嵌 StarlingMonkey JS 引擎，所以产物 ~12MB） |
| `prelude.d.ts` | 用户写 TS 工具时的类型声明（`httpFetch`/`readFile`/`run` 的签名），编辑器提示用 |
| `samples/*.js` | 四个样例：echo（最小工具）、fuel_bomb（死循环）、net_attempt（网络越权）、output_flood（输出洪水）——后三个就是恶意样本测试的弹药 |

**用户 JS 的约定**：导出 `export function run(input) { return "结果"; }`；要发请求就 `import { httpFetch } from "folio:sandbox/host"`（同步调用，返回 JSON 字符串）。M3 DIY 上线时，用户提交 TS 源码 → 平台在线跑 build.ts → 存 wasm（M1 先手动编译）。

### 3.4 测试（test/）

#### `test/conftest.py` —— 测试基础设施

一个值得学的工程点：session 级 fixture 把沙箱池挂在**专属后台线程的 event loop** 上（`ThreadedSandbox`），测试以同步方式调用——绕开 pytest-asyncio 的 function/session loop 割裂问题（session fixture 建的 Future 挂在 loop A，测试跑在 loop B，跨 loop Future 直接报错）。`build_or_load_wasm` 自动按需编译样例并缓存到 /tmp。

#### `test/unit/` —— 机制层单测（不碰进程）

- `test_contracts.py`：帧编解码 roundtrip、错误码值锁定（稳定性契约）
- `test_allowlist.py`：白名单全分支（子域/后缀伪装/大小写/端口/IP/私网/坏 URL）
- `test_limits.py`：钳制全方向（放宽压回/收紧生效/硬顶封顶）
- `test_truncate.py`：`_truncate` 直测（大 stdout/result/stderr、UTF-8 多字节截断安全）——**这就是 JS 路径输出截断的覆盖方式**

#### `test/malicious/` —— M1 验收（每个文件对应 ADR-0001 的一条）

| 文件 | 验收语义 | 关键断言 |
|---|---|---|
| test_01 | 死循环必须被确定性中断 | Python 墙钟 timeout；JS fuel 断（上游 bug 语义下为 panic→ENGINE_CRASH）+ **池自愈后立即可用** |
| test_02 | 内存炸弹有界 | 2.5GB 被 OverflowError/堆上限拦；JS 8MiB 实例化拦截；64MiB 默认档不误伤 |
| test_03 | 文件系统逃逸 | /etc/passwd 读不到（BLOCKED）；os.system 是静默 stub 但**无真实执行**（uid= 不出现）；socket 对象可建但 connect 必然 OSError |
| test_04 | 网络越权全拒+留痕 | evil 域名/127.0.0.1 全拒、拒因正确、**NetEvent 每次尝试都有记录**；直接 fetch 被禁 |
| test_05 | 输出洪水截断 | ok=True + OUTPUT_TRUNCATED + 长度不超限 + 截断标记 |
| test_06 | 跨调用零状态泄漏 | A 写文件 B 读不到；输入文件只在携带它的调用内可见 |
| test_07 | sidecar 死亡自愈 | kill 进程 → 池容量恢复 → 请求立即可用；进行中请求收到明确错误不挂起 |

**读测试是理解验收标准最快的方式**——每个断言都对应一条安全不变量。

## 4. 十个核心设计决策（为什么）

**D1 —— 为什么协议是行分隔 JSON 而不是 HTTP/gRPC？**
stdin/stdout 管道没有监听端口、没有 socket 文件——**攻击面最小**。sidecar 不需要任何网络栈，"沙箱不能上网"从物理上成立（它自己都收不到网络请求）。行 JSON 肉眼可调试（`echo '...' | python -m src.sandbox.sidecar`）。协议帧与传输是解耦的（contracts.py 不知道 stdin/stdout 的存在），将来要换 UDS 零改动。

**D2 —— 为什么每请求全新 Store / 全新 runner 进程？**
跨调用状态泄漏（test_06）靠"物理隔离"保证，不靠"逻辑清理"——清理逻辑漏一条就是漏洞，物理隔离没有这个问题。代价：JS 每次 ~700ms（编译缓存摊薄）、Python 每次 ~1s 冷启动。工具调用场景这个延迟可接受（LLM 思考本身就要几秒）。

**D3 —— 为什么 sidecar 单飞（一次一个请求）？**
最简单的资源记账模型：fuel/内存配额按 Store 独立，不需要跨请求共享任何锁。并发需求由池横向扩（sidecar_pool_size=2 起步，配置可调）。串行还带来一个安全红利：**一个恶意请求最多占用一个 sidecar，永远不会抢占别的请求的配额**。

**D4 —— 为什么 allowlist 检查在进程 B，请求代理从进程 C 转发回来？**
如果检查逻辑在 runner.js（进程 C）里，它和用户代码同进程——用户代码可以篡改/直接调底层绕过。转发回进程 B 意味着检查代码在**不可信代码够不到的地址空间**里执行。宁可多一次进程间往返。

**D5 —— 为什么 fuel 和墙钟双机制？**
fuel 是**确定性**计量（第 N 条指令精确中断，无抖动、可计费）；墙钟是**普适**兜底（Python 没有 fuel）。两者互补：JS 靠 fuel 防烧钱、epoch 墙钟防卡死；Python 靠墙钟。上游 bug（fuel 耗尽 panic）发生时墙钟+进程池自愈兜底——**纵深防御不是口号，是每层失效时下一层接住**。

**D6 —— 为什么 fuel 默认 1e9？**
实测数据：最小 JS 工具一次 9.4M（初始化占 8.5M）；`repeat(2MB)` 按字符计费能烧掉 >2e9。默认给百倍余量（1e9）让正常工具不受限，同时死循环防护依然成立——10 秒墙钟内死循环烧掉的 fuel 远超任何预算，fuel 或墙钟先到都会拦住。

**D7 —— 为什么 selfdestruct 只对 ENGINE_CRASH 计数？**
被恶意样本测试打脸后的修正：业务错误码（fuel/timeout/denied）是对坏代码的**正常响应**，不是引擎坏了。原设计把它们也计数，17 个测试里的预期失败就把健康 sidecar 逼自杀了。修正后的语义：引擎层异常才算"这台机器可能不稳了"。

**D8 —— 为什么 WIT 协议全用 string？**
wasmtime-py 对 WIT 复合类型（option/result/record）的 Python 编解码支持不完整。string 是唯一绝对稳的公共类型，复合语义（错误对象、状态码+响应体）用 JSON 字符串承载，两端各自解析。类型安全损失换来的是实现零风险——正确的工程权衡。

**D9 —— 为什么 Node 堆限制独立于 memory_limit_mb？**
`--max-old-space-size=64` 会误杀：Pyodide 运行时（V8 堆 + wasm 引擎）自身就要 ~200MB。所以 Node 堆给固定余量（max(256, limit)），Python 代码能用的内存靠另外两道防线：Linux RLIMIT_AS（地址空间级，64MB 真硬限）和 wasm 堆编译期上限 2GB（全平台兜底）。

**D10 —— 为什么审计事件由响应帧回传、API 侧统一落盘？**
sidecar 以低权限运行（无 home、无 shell）——**也不该有审计目录的写权限**。网络访问记录随 done/result 帧回传，进程 A 的 audit.py 统一落盘。副作用：审计与业务结果在同一个事务边界，不会出现"执行成功但审计丢了"的窗口。

| 攻击 | 防线（哪层拦住） | 验证测试 |

## 6. 踩过的坑（按时间序，都有测试或注释锁定）

1. **wasmtime-py C API 缺 `set_wasi` → Rust panic**：`add_wasip2()` 挂的宿主实现（clocks/random）从 Store 的 WasiCtx 取状态，没设就在用户代码第一次调 `Date.now()` 时 panic（46-49 版全存在）。修：`store.set_wasi(WasiConfig())` + `store.set_wasi_http()`。
2. **linker 句柄锁**：`root().add_instance()` 返回的句柄存活期间 linker 被锁，instantiate 报错。修：`with` 作用域。
3. **fuel 耗尽是 panic 不是 trap**（上游 bug）：JS 死循环烧尽 fuel 时 C API 直接 SIGABRT。已接受：墙钟为主防线、池自愈兜底，语义落在"攻击有界+服务可用"。
4. **Node pipe 异步写大帧被 exit 腰斩**：2MB done 帧写出后立即 `exit(0)`，帧尾丢失、JSON 解析失败。修：写完成回调里退出。
5. **asyncio 流 64KB 行上限**：manager 读 1MB result 帧触发 LimitOverrunError，误判 sidecar 死亡。修：`create_subprocess_exec(limit=32MB)`。
6. **`pyodide.globals.set` 注入对 `from js import` 不可见**：写的是 Python `__main__` 命名空间而非 JS globalThis。
7. **Pyodide 只返回 Expr 语句的值**：读 result 变量的辅助代码以 if/else 结尾时永远返回 None。修：函数定义 + 裸调用表达式。
8. **坏 wasm 触发 sidecar 自杀**：instantiate 失败（imports 不匹配/fuel 在初始化阶段耗尽）曾被映射为 ENGINE_CRASH——它是 fatal，直接把 sidecar 逼自杀（rc=3）。教训：**错误码的 fatal/非 fatal 边界就是进程稳定性边界**——用户输入能引发的错误永远不该是 fatal。修：instantiate 期的 WasmtimeError 按 trap 消息细分（fuel→FUEL_EXHAUSTED、epoch→TIMEOUT、memory→OOM、其余→BAD_CODE），test/unit/test_engine_wasm.py 锁定防回归。

cd folio-agent-server

import base64, json, subprocess, sys
code = base64.b64encode(open('/tmp/echo.wasm','rb').read()).decode()
frame = {'type':'exec','id':'j1','lang':'js','code':code,'input':'你好'}
p = subprocess.run([sys.executable,'-m','src.sandbox.sidecar'],
                   input=json.dumps(frame), capture_output=True, text=True)
print(p.stdout.splitlines()[-1])"
