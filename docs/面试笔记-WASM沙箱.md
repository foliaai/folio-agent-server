# WASM 沙箱 · 面试笔记（大白话版）

> 用法：§1 背熟开场 → §2 顺着讲 → §3/§4 是论证核心 → §5/§6 是追问时的答案

---

## 1. 三十秒开场白（背这段）

> "我的平台要跑别人写的代码——用户自己定义的工具，还有 AI 生成的代码，都不能信任。我做的沙箱方案是：把代码编译成 WASM 格式，放在单独的进程里跑。最大的特点是**安全不靠配置，靠天生**——恶意代码在 WASM 里根本'没有手段'去越界，就像被关在一个没有门的房间里。再配上'跑多少条指令就停'的计数器、到点强制停的闹钟、所有联网请求必须经过我检查的统一出口。最后我用七种攻击手段做测试——死循环、撑爆内存、偷读文件、偷连外网、刷屏输出、留后门、直接杀进程——全部挡住，服务还自动恢复。"

---

## 2. 原理怎么讲（两分钟）

### 2.1 核心一句话：两种"墙"的区别

- **Docker 这类容器的墙**：代码还是能看见整个操作系统，只是"规定"它不许乱动（靠一堆规则拦着）。规则是人写的，就可能写漏；拦规则的系统本身也有漏洞，历史上出过好几次容器越狱事件。
- **WASM 的墙**：代码被编译成一种受限格式，**这种格式里压根没有"访问任意内存""调用系统函数"这类指令**。它想干坏事，但语言里没有这个动词。

打个比方：**容器是"不许翻墙"，WASM 是"没有梯子"**。前者靠规矩，规矩会漏；后者靠结构，结构绕不过去。

### 2.2 三道保险（每道一句话）

| 保险 | 大白话 | 为什么好 |
|---|---|---|
| **指令计数器（fuel）** | 每执行一条指令扣一格油，油用完立刻停 | `while True` 死循环会在**精确的第 N 步**被掐断——这个精确性还能拿来做计费 |
| **闹钟（超时）** | 到时间就打断执行 | 兜住计数器管不到的情况（比如卡在网络请求上） |
| **内存上限** | 内存用到某个数就不再给 | 撑爆内存的攻击在"要内存"那一步就被拒了 |

对比：Docker 的资源限制都是"**事后补救**"（超了才杀进程）；WASM 是"**事前说好**"，这两种的可靠性完全不同。

### 2.3 "没有门"的房间，怎么放东西进去？

代码需要什么能力（读文件、发请求），必须**提前声明**，由我的程序提供——不声明，这能力在它的世界里就不存在。

而且有个关键设计：**检查在别的进程里做**。用户代码想发请求，只能"举手申请"，我的沙箱管家（另一个进程）替它去发、发之前检查白名单——用户代码就算被玩坏，也碰不到检查逻辑本身。

### 2.4 结构图（白板边画边讲）

```
我的服务器（FastAPI）
   │  管道传 JSON
沙箱管家进程（JS 代码在这里跑，权限很低）
   │  管道传 JSON
一次性小进程（Python 代码在这里跑，用完即扔）
```

面试官必追问的两个"为什么"：

- **为什么要单独进程？** WASM 这堵墙挡的是"墙里的代码"，挡不住"WASM 软件本身"的 bug。业界有过真实案例：一个 WASM 运行时的漏洞连累了七家产品，就是因为他们把沙箱和业务跑在同一个进程里。加一道进程隔离 = 双保险。
- **Python 为什么再单独一层、用完就扔？** Python 那个运行时（Pyodide）自己的设计就假设"代码是可信的"，不能指望它防守。所以放到一个一次性的小进程里，跑完整个进程销毁——顺便做到了**两次执行之间绝对不留痕迹**（想留后门？房间都没了）。

## 3. 和其他方案比（速记表）

| | Docker 容器 | 迷你虚拟机 | **我的 WASM 方案** |
|---|---|---|---|
| 怎么隔离 | 规则拦着（会漏） | 模拟一台电脑 | **格式里没有越界手段** |
| 启动一次 | 秒级 | 百毫秒级 | **毫秒级** |
| 占用 | 一整套系统 | 一台"电脑" | **几十 MB** |
| 资源控制 | 事后杀 | 事后杀 | **事前定死** |
| 默认能力 | 什么都有（做减法） | 什么都有 | **什么都没有（用啥申请啥）** |
| 语言限制 | 没有 | 没有 | **有（Python 只支持部分包）** |

记住每个优势的因果：启动快是因为"开个新执行环境只是分配内存"；默认什么都没有是因为"能力要申请"；控制精确是因为"按指令计数"。

## 4. 为什么适配我的系统（面试的核心加分项）

> 讲法：先摆四个条件，再一个个排除——展示的是**你怎么做决策**，不是背结论。

我的场景四个硬条件：

1. **跑的是不信任的代码，还是多用户的** → Docker 这类"规则式"隔离不够格，先排除；
2. **每次只跑一小段、但是很频繁**（一次工具调用就是一次执行）→ 需要毫秒级启动和极小开销，迷你虚拟机每次启动百毫秒起步、还要背一整台"电脑"的内存，撑不住高频，排除；
3. **必须自建、数据不能出公司** → E2B 那种花钱托管的方案，排除；
4. **部署就是单机 Docker，没有 K8s 集群** → 基于 K8s 的那套方案，为一个沙箱引入整套集群不值得，排除。

排除到最后，**WASM 是唯一同时满足四个条件的**——不是我偏爱它，是场景刚好卡在它的甜区。

**主动交代代价（加分）**：Python 只能用部分包（不能用需要多线程、网络底层的东西）。我的处理是把它变成**明确的产品边界**——告诉用户"工具适合做数据计算类的事"；将来真有 heavier 的需求，接口不用改，把底层执行换成迷你虚拟机就行，架构上留了后路。

## 5. 实测数字（背三四个就够）

| 事实 | 数字 | 大白话 |
|---|---|---|
| 最简单的 JS 工具跑一次 | 约 940 万步指令、700 毫秒 | 计费和配额的基准 |
| Python 跑一次 | 约 1 秒 | 用冷启动换最强隔离，值 |
| 拼一个 2MB 的字符串 | 超过 20 亿步指令 | 字符串操作按字符计数——所以默认给了 10 亿步，正常工具用不完、死循环必被拦 |
| 攻击测试 | 7 种全挡住 | 死循环/爆内存/偷文件/偷联网/刷屏/留后门/杀进程，服务全部自愈 |

## 6. 追问快答（每个两三句）

**Q：Docker 不是也能隔离吗？**
它靠规则拦，规则会配漏、拦截系统自己也有过越狱漏洞；而且默认什么能力都有，等于一直在做减法。我的场景是多用户高频跑小段代码，容器的秒级启动和整套餐具的重量都不合适。

**Q：WASM 自己就没漏洞吗？**
有，运行时软件本身也是代码、也会有 bug。我的对策是纵深防御：沙箱放独立进程，运行时炸了也伤不到业务；我还真踩过一个上游 bug（指令数耗尽时它不优雅停止而是直接崩），靠"闹钟兜底 + 进程池自动重启"接住了。**一层失效，下一层接住**。

**Q：怎么防止代码偷连内网、偷传数据？**
四道检查：只许 HTTPS、不许直接写 IP 地址（白名单按域名管）、内网地址全拒、**域名解析完再看一眼真实 IP 是不是内网**（防"域名指向内网"的把戏）。所有联网尝试都记日志，被拒的也记。

**Q：两次执行之间会不会串数据？**
不会，物理上不可能串：JS 每次开全新的执行环境，Python 每次开全新进程。有专门测试：上一次写文件，下一次读不到。

**Q：性能会不会太慢？**
JS 700 毫秒、Python 1 秒左右。但这个场景里 AI 思考本身就要好几秒，沙箱开销占比很小，而且池化和编译缓存还在摊薄它。

**Q：沙箱进程被搞挂了怎么办？**
进程池设计：一个沙箱同时只接一单（坏代码最多占住一个），挂了自动重启新的，正在跑的请求会收到明确报错而不是卡死。有测试：手动杀掉进程，几秒后池子恢复，请求照常跑。

**Q（反问面试官，展示视野）：** 如果场景是"给 AI 一个带浏览器的完整桌面环境"，我会选容器方案加隔离层——不同的执行粒度配不同层的沙箱，WASM 只在"小段代码、多用户、高频"这个交集里是最优解。

---

## 7. 收尾一句话

> "一句话总结：WASM 沙箱是让坏代码**没有手段**，而不是**不许动手**——顺带换来精确到条的资源控制和毫秒级的启停。代价是语言上有些限制、运行时本身要多包一层进程。在我这个多用户、跑小段代码、自己部署的场景里，这笔账是划算的。"
