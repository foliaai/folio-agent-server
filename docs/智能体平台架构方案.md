## 0. 背景与动机

AI-site 前端的两个未开放模块需要后端支撑：

- **首页**：通用智能体服务——一个对话式强 agent，配备通用工具面（Web 搜索、代码执行、知识库检索）。
- **智能体页（/agents）**：用户 DIY 智能体——自行编写 system prompt、选择模型、定义工具。

旧方案（deepresearch 设计文档）基于 2025 年的"多角色协作流水线"范式（Commander→Researcher→Critic→Writer 固定图）。该范式已被 2026 年的实践与研究所否定：

- Nature Machine Intelligence（2026-07，260 种配置）：多 agent 仅在**可并行拆分**任务上有收益（最高 +80.8%）；顺序依赖强的任务最高 **-70%**；SWE-bench Verified 上四类多 agent 架构**全部负收益**。
- Anthropic 多 agent 研究系统实测：普通 agent token 消耗约为聊天 4 倍，多 agent 系统 **15 倍**。
- 2026 年主流收敛为：**单强模型 agent loop + 按需 subagent 扇出**，配套四个标准件——MCP（工具）、Agent Skills / SKILL.md（知识）、沙箱（执行）、LiteLLM（模型路由）。

**v2 修订动机**：v1 评审发现四处架构级缺口——① 技能层与现有 skill-service / skill_core 生态的关系未定义（v1 误将 AKS 当作技能数据主人）；② 双运行时（SDK + Pydantic AI）必要性论证不足；③ 多后端部署拓扑（端口、路由、WS 代理）完全缺失；④ subagent 扇出引用了"15× token"证据却没有任何成本护栏。本版针对以上修订，决策记录见 ADR-0003。

## 1. 产品形态

### 1.1 首页：通用智能体

一个预配置的对话式 agent：

- 对话 + 流式输出（复用现有知识库对话的 WebSocket 协议与前端组件：思考流、工具轨迹时间线、引用 chip）。
- 通用工具面：
  - `web_search`：Web 搜索（Tavily 已在依赖中）。
  - `code_execute`：沙箱代码执行（§4）。
  - `kb_retrieval`：检索 `agentic_knowledge_system` 的知识库（跨服务调用，只读）。
  - `skills`：Agent Skills 加载（§5）。
- subagent：主 agent 判定任务需要广度时（如多路信息搜集），通过 agent-as-tool 模式按需扇出并行 subagent，每个 subagent 是同一个 loop 的轻量实例。**不做预定义角色流水线**。扇出全程受 BudgetLedger 成本护栏约束（§7）。

### 1.2 智能体页：DIY 智能体

用户可创建的智能体 = 一份**声明式定义**（AgentSpec，YAML/JSON，平台自研 Pydantic 模型）：

```yaml
model: litellm-proxy:deepseek-v4-flash
instructions: |
  你是{{user_name}}的运营数据助手，输出一律使用中文。
deps_schema:
  type: object
  properties: { user_name: { type: string } }
  required: [user_name]
output_schema:          # 可选：结构化输出（SDK output_type，运行时强校验）
  type: object
  properties:
    answer: { type: string }
    confidence: { type: number }
capabilities:            # 平台注册表中的工具，用户勾选
  - WebSearch: { max_results: 5 }
  - CodeExecute: { language: python }
  - KbRetrieval: { scope: "kb:my-kb" }
skills: [data-analysis]  # skill-service 中的技能（§5）
budget:                  # 预算上限（§7，BudgetLedger 强制）
  session_tokens: 500000
retries: 2
tool_timeout: 30
```

运行时链路：`AgentSpec`（`src/diy/spec.py`）→ 编译层（`src/diy/compile.py`）→ OpenAI Agents SDK 的 `Agent` 实例。**不引入第二套运行时**（ADR-0003 D1）。前端表单 ↔ YAML 双向转换由 `AgentSpec.model_json_schema()` 产出的 JSON Schema 驱动。

**能力边界（产品文案需明确）**：用户工具是"数据变换/计算"型（纯函数式、确定性输入输出），不是"任意 Python 生态"型。理由见 §4。

## 2. 总体架构

```
浏览器（AI-site，Next.js dev :4001）
  │  唯一入口：NEXT_PUBLIC_API_URL = http://localhost:4000（本地网关；生产为域名）
  ▼
Caddy 统一网关（:4000 本地 / :443 生产，见 §8）
  ├── /api/chat/*  /api/knowledge/*      → agentic_knowledge_system（:8000）
  ├── /api/v1/*                          → agent_apps（:8002）
  └── /skill-api/*                       → skill_service（:8001）
        │
        ▼
agent_apps 后端（本仓库，FastAPI，:8002）
  │
  ├── 统一运行时：OpenAI Agents SDK（首页 loop 与 DIY 共用，ADR-0003 D1）
  │     ├── 模型接入：set_default_openai_client(base_url=LiteLLM proxy)
  │     │   —— 复用现有网关，不引入 litellm Python 库（其 SDK 集成是 beta）
  │     ├── subagent：agent-as-tool（@function_tool 包装 Agent）按需扇出
  │     │   —— 受 BudgetLedger 三层护栏约束（§7）
  │     └── DIY 编译层（src/diy/）
  │           ├── spec.py     # AgentSpec Pydantic 模型（+ model_json_schema 出表单 schema）
  │           ├── compile.py  # spec → agents.Agent：模型映射 / capabilities 装配 /
  │           │               #   instructions 模板变量构造期校验
  │           ├── budget.py   # BudgetLedger（与首页 loop 共用，§7）
  │           └── store.py    # spec YAML 原文 + 解析结构 + 权限 → MySQL
  │
  ├── 工具层（两个场景共享，锁死这条线）：MCP 协议
  │     ├── web_search      （内置 MCP server）
  │     ├── code_execute    （→ 沙箱 sidecar，§4）
  │     ├── kb_retrieval    （HTTP 调 agentic_knowledge_system）
  │     └── 用户自定义工具   （→ 沙箱 sidecar，§4）
  │
  ├── 技能层（§5）：HTTP 只读调 skill-service
  │     （复用 AKS 的 SkillServiceRepository 模式；SKILL.md 格式由 skill_core 统一）
  │
  └── 沙箱执行：独立 sidecar 进程（详见 adr/0001）
        └── Wasmtime
            ├── JS/TS 用户工具：编译 wasm32-wasi
            ├── Python 用户工具：Pyodide（接受包生态约束）
            └── I/O 全部经宿主函数（fetch allowlist / 内存 FS）
```

### 2.1 关键决策一览

| # | 决策 | 理由 | 详见 |

| D5 | 模型全走现有 LiteLLM proxy | 复用 agentic_knowledge_system 的网关与模型清单 | §6 |
| D6 | 不引入 LangGraph 作为地基 | 编排按需再议（当前无此需求）；范式已过时 | §9 |
| D7 | **技能层唯一持有者 = skill-service**，SKILL.md 下沉 skill_core | 三后端复用既有生态；避免出现第三套技能数据源 | §5 / ADR-0003 D3 |
| D8 | **Caddy 统一网关 + 固定端口约定** | 单域名单入口；WS 透传；消除端口冲突 | §8 / ADR-0003 D4 |
| D9 | **subagent 扇出受 BudgetLedger 硬约束** | 防"多 agent 15× token"失控 | §7 / ADR-0003 D5 |

## 3. 工具层：MCP

所有工具（内置 + 用户自定义）统一包装为 MCP server，运行时只做 MCP client：

- **内置工具**：平台代码实现，注册表带元数据（名称、描述、参数 schema、权限级别）。
- **用户自定义工具**：用户提交的代码经沙箱执行（§4），包装为 per-agent 的 MCP 工具，schema 由代码注解（TS）或函数签名（Python）导出。
- **权限模型**：工具分 `built-in / user-code / external-api` 三级；`external-api`（用户申请的网络出口）需要在 DIY 表单里显式申请域名 allowlist，默认全拒。

**为什么统一运行时后仍要 MCP**：v1 的理由（双运行时工具格式互通）已不成立，v2 的理由是**运行时可替换性保险**——SDK 处于 0.x，若出现重大 breaking change 或弃坑，工具层零改动即可切换运行时；同时用户自定义工具（沙箱 sidecar 中的代码）与内置工具收敛为同一注册表形态。代价：需管理 MCP server 进程的生命周期（健康检查、连接池）——接受。

## 4. 沙箱执行（详见 ADR-0001）

摘要（细节、威胁模型、资源限制见 ADR）：

- **进程拓扑**：API 服务器 spawn 独立 sidecar 进程，sidecar 内 Wasmtime 每次工具调用一个独立 store。
- **硬约束**：fuel/epoch 计量 CPU、wall-clock 超时、内存上限、零默认文件系统、零默认网络。
- **网络出口**：唯一通道是宿主函数 `http_fetch(url, opts)`，按 per-agent allowlist 过滤（域名 + 方法 + 大小上限），全量审计日志。
- **语言支持**：JS/TS 为主推（编译 wasm32-wasi，无运行时限制）；Python 经 Pyodide（无 threading/sockets/ssl-stub、包生态受限——产品能力边界以此为准）。
- **红线**：绝不把 Pyodide/Wasmtime 嵌入 API 服务器进程。DEF CON 34（Pyodide 缺陷打穿七个产品）与 Cohere Terrarium 漏洞是前车之鉴。

## 5. 技能层：统一走 skill-service

### 5.1 现有技能生态（整合基线）

| 组件 | 角色 | 现状 |
|---|---|---|
| **skill_core** | 核心包（runtime/ORM 无关）：SkillDescriptor / SkillRegistry / SkillRepository 协议 + MySQL 适配 | v0.2.3，以 wheel 手动拷贝分发 |
| **skill_service**（:8001） | 技能**唯一写入口**（独占 MySQL + MinIO 封面），REST API | 已上线，前端 /skills 页在用 |
| **agentic_knowledge_system** | HTTP 只读消费者（SkillServiceRepository over httpx，内置 + custom 技能合并） | 已上线 |

### 5.2 本平台的接入原则

**agent_apps 不做第三套技能数据源**，照抄 AKS 的消费模式：

```
skill_core（SKILL.md 解析与渐进披露下沉于此）
   │  依赖方式：uv path / git 引用（废弃 wheel 手动拷贝）
   ├─► skill_service           （唯一写入口，MySQL 持久化，SKILL.md 持有者）
   ├─► agentic_knowledge_system（只读：HTTP /skills/*）
   └─► agent_apps              （只读：HTTP /skills/*，复用 AKS 的实现模式）
```

- **SKILL.md 对齐在 skill_core 实现**：frontmatter 解析、Level 0/1/2 渐进披露加载做进核心包，三个消费方共用，不存在"各自适配层"。skill_service 升级为 SKILL.md 的持有者；AKS 既有技能表经一次性迁移脚本转为 SKILL.md 存回 skill_service。
- **agent_apps 接入**：复制 AKS 的 `src/service/skill/`（`service_repo.py` + `registry_singleton.py`，约 200 行），`SKILL_SERVICE_URL` 指向同一实例；首页 agent 的 `@skill` 调用与 DIY AgentSpec 的 `skills` 字段共用同一 Registry。
- **分发方式修正**：废弃 `third_party/` wheel 手动拷贝（AKS 内已堆 0.2.1/0.2.2/0.2.3 三个版本，漂移已经发生），改为 uv 的 path（本地开发）或 git tag（部署）引用。
- **前端不变**：/skills 页继续走 skill-service（经网关 `/skill-api/*`），技能 CRUD 入口仍是 skill_service 一处。

## 6. 模型层

- 唯一入口：现有 LiteLLM proxy（`agentic_knowledge_system` 侧部署，model lake / litellm 双模式已支持）。
- OpenAI Agents SDK：`set_default_openai_client(AsyncOpenAI(base_url=proxy))`，模型字符串即 proxy 的模型 id（`litellm_proxy/deepseek-v4-flash` 等）。
- **DIY 模型白名单**：用户可选模型 = `/api/chat/models` 清单的子集（沿用现有 provider 分组与 thinking_levels 元数据）。
- Token 计量：每次运行记录 usage；**预算硬上限由平台 BudgetLedger 统一实现（§7），首页 loop 与 DIY 共用**，per-agent 日/月上限在 AgentSpec 的 `budget` 字段中声明。

## 7. Subagent 成本护栏

### 7.1 设计原则

**预算不是检查点，是账本**：主 loop 与所有 subagent 的 LLM 调用共享同一个 `BudgetLedger`（`src/diy/budget.py`），每次调用前原子扣减，扣不动即拒绝。**降级优先于失败**——预算耗尽不是报错，而是收敛任务、用现有材料收尾。

### 7.2 三层限制

| 层 | 参数 | 默认值 | 机制 |
|---|---|---|---|
| **结构层**（防扇出失控） | `max_fanout_depth` | **1**（写死） | subagent 的工具列表里**不含** `spawn_subagent`——用能力授予而非 prompt 约束 |
| | `max_concurrent_subagents` | 3 | 信号量；超出的排队 |
| | `max_subagents_per_session` | 10 | 会话级计数器 |
| | `subagent_max_turns` | 8 | SDK `RunConfig.max_turns`；subagent 是窄任务 |
| **预算层**（防烧钱） | `session_token_budget` | 500k（会话建立时可配） | Ledger 原子扣减，input+output+cache 全计 |
| | `daily_user_budget` | 2M | Redis 计数，跨会话 |
| | `subagent_budget_share` | 会话剩余预算的 **40%** | 扇出前检查：剩余 × 40% < 单 subagent 预估成本 → 拒绝扇出，主 loop 继续 |
| **行为层**（防过度触发） | 扇出判定 prompt | — | 明示"仅在任务可并行拆分为 ≥2 个独立信息需求时扇出" |
| | 规则前置拦截 | — | 单跳问题 / 已有引用可直接回答时跳过扇出 |

### 7.3 熔断语义

- **80%**：向主 loop 注入系统消息"预算接近上限，收敛任务"；新扇出被拒，**进行中的不中断**。
- **100%**：拒绝一切新 LLM 调用；主 loop 用现有材料生成收尾回答；事件流推 `budget.exceeded`（§8.3），前端显示"已达本会话预算上限"。
- 实现：`asyncio.Lock` 保护（单进程）+ Redis 持久化（断线重连后恢复会话预算）。

### 7.4 可观测

每次扇出记录 `{session_id, trigger_reason, count, tokens_total, tokens_per_sub, duration}`；上线两周后据真实数据回调 `max_concurrent_subagents` 与预算比例，不拍脑袋定参。

## 8. 统一入口与 WebSocket 协议

### 8.1 问题（v1 缺失，v2 补齐）

1. 前端单一 `NEXT_PUBLIC_API_URL` 指向 :8000，但 AKS / agent_apps / skill_service 各有独立路由空间；
2. agent_apps `main.py` 默认端口 8001 与 skill_service 的 8001 冲突；
3. Next.js rewrites 不能可靠代理 WebSocket，`/skill-api` 的 rewrite 模式不能推广到对话流。

### 8.2 网关与端口约定

```
Caddy（本地 :4000，生产 :443，同一份配置改域名即可）
```

```caddyfile
:4000 {
    handle_path /skill-api/* {
        reverse_proxy 127.0.0.1:8001
    }
    handle /api/chat/* {
        reverse_proxy 127.0.0.1:8000
    }
    handle /api/knowledge/* {
        reverse_proxy 127.0.0.1:8000
    }
    handle /api/v1/* {
        reverse_proxy 127.0.0.1:8002
    }
}
```

| 服务 | 端口（本地） | 说明 |
|---|---|---|
| Caddy 网关 | **4000** | 生产 443；WS 透传零配置 |
| agentic_knowledge_system | 8000 | 不变 |
| skill_service | 8001 | 不变 |
| **agent_apps** | **8002** | **`main.py` 默认值从 8001 改 8002**，消除与 skill_service 冲突 |
| AI-site（Next dev） | 4001 | 直连 4000 网关 |

- 前端：**删除** `next.config.mjs` 的 `/skill-api` rewrite，统一走网关；`.env` 只留一个 `NEXT_PUBLIC_API_URL=http://localhost:4000`。
- 鉴权：**各后端本地校验** Logto JWT（AKS 已有 `get_current_user_id_ws`，模式可复制），网关只透传不做鉴权——后端可直连调试，网关不成为逻辑单点。
- 心跳与重连：沿用现有 `ping/pong`（客户端 30s）；前端统一指数退避重连（1s→2s→5s→10s 封顶）；重连后凭 session_id 拉历史消息恢复现场（AKS sessions API 已支持）。

### 8.3 统一 WS 信封协议

AKS 现有帧协议升格为**平台协议**，agent_apps 的首页 agent WS 直接复用，只增不改：

| 帧 | 方向 | 归属 | 说明 |
|---|---|---|---|
| `start` / `stop` / `ping` | C→S | 平台协议 | 与 AKS 现有一致 |
| `ready` / `session.ready` | S→C | 平台协议 | |
| `thinking.delta` / `content.delta` | S→C | 平台协议 | |
| `tool_call.started` / `args_delta` / `done` | S→C | 平台协议 | |
| `usage` / `done` / `error` / `pong` | S→C | 平台协议 | |
| `retrieval.started/progress/done`、`citation` | S→C | AKS 专属 | agent_apps 不发；前端 handler 按 endpoint 注册 |
| `subagent.started` / `subagent.done` | S→C | **agent_apps 新增** | 携带 name / budget 字段，配合 §7 护栏透出 |
| `budget.warning` / `budget.exceeded` | S→C | **agent_apps 新增** | 配合 §7 熔断语义 |

- 前端：`useKnowledgeChat` 泛化为 `useAgentChat(endpoint, handlers)`——事件分发表按后端注册，知识库面板与首页通用面板是两个 handler 集合，连接管理/重连/心跳一套代码。
- 协议落档 `docs/ws-protocol.md`（AKS 与 agent_apps 共同遵守），帧类型枚举放一份共享 JSON Schema 供两边对照。

## 9. 非目标（明确不做）

1. **预定义多角色流水线**（旧 deepresearch 方案）——范式已证伪，归档处理。
2. **LangGraph 图编排**——当前产品无 checkpoint 长流程需求；未来若有，作为按需组件引入，不作地基。
3. **通用 Python 生态沙箱**（任意 pip 依赖、任意网络）——WASM 约束即产品边界；需要重型计算时未来评估 microVM 方案（E2B 自建），不在本期。
4. **Agent 执行的编辑器接入**（ACP 协议）——记录在案，非本期。
5. **durable execution / 长流程 checkpoint**——这是保留 Pydantic AI 的唯一场景；届时按需引入，AgentSpec 是平台自有格式，迁移面小。

## 11. 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| M1 沙箱安全基线 | sidecar 进程 + Wasmtime；一个 JS 工具 + 一个 Pyodide 工具；fuel/超时/内存限制；fetch allowlist + 审计日志 | 恶意样本测试（死循环→fuel 断；内存炸弹→OOM kill；越权域名→拒+审计） |
| M2 入口与首页 loop | **Caddy 网关 + 端口约定落地（agent_apps 改 8002，前端删 rewrite、单 BASE_URL）**；SDK 接 LiteLLM proxy；web_search 一个工具；WebSocket 流式对齐平台协议（§8.3） | 前端单 BASE_URL 经网关访问三后端；首页可对话，工具调用可见 |
| M3 DIY 运行时 | **AgentSpec 薄层（spec/compile/budget/store）+ 同一 SDK 执行**；CodeExecute 接 M1 沙箱；AgentSpec JSON Schema 驱动的表单 | 用户创建一个带自定义工具的 agent 并跑通 |
| M4 护栏与技能 | **BudgetLedger + subagent 扇出（含熔断与事件透出）**；技能层接入（skill-service 只读 + SKILL.md） | 扇出受预算硬约束（恶意扇出场景不超额）；@skill 可用 |

每阶段独立可叫停；M1 是安全前提，不通过则整体重新评估沙箱技术（备选：microVM/E2B 自建）。M2 的网关部分与 M1 无依赖，可并行先行。
